# Secure SDLC — how SecureNotes was built

How security was handled at each stage of the software development life cycle, with a
link to the evidence for each claim.

| Stage | What was done | Evidence |
|---|---|---|
| **1. Requirements** | Security requirements written before code: private notes per user, no plaintext passwords, no secrets in the repo, safe behind a TLS proxy | [README — security controls](../README.md#security-controls-so-far) |
| **2. Design** | STRIDE threat model per element, mapped to MITRE ATT&CK; trust boundaries drawn; open risks listed and fed into later phases | [threat-model.md](threat-model.md), [data-flow diagram](threat-model-dfd.html) |
| **3. Implementation** | Secure defaults in code: Argon2id, CSRF tokens, owner-scoped queries, autoescape + strict CSP, security headers, input limits, secrets from the environment only | [`app/security.py`](../app/security.py), [`app/main.py`](../app/main.py) |
| **4. Verification** | A test for every control, including hostile-input and production-mode tests; four CI gates on every pull request and weekly | [`tests/`](../tests), [security.yml](../.github/workflows/security.yml) |
| **5. Release** | Changes reach `main` only through pull requests with all gates green (branch ruleset); third-party CI actions pinned to commit SHAs | [Pull requests](https://github.com/skenderaje/Secure-notes/pulls?q=is%3Apr) |
| **6. Deployment** | Production config in code ([`render.yaml`](../render.yaml)), tested but deliberately not hosted (see below); `SECRET_KEY` generated by the host, database URL set in the dashboard, never committed; HSTS and `Secure` cookies; API docs off | [`tests/test_production.py`](../tests/test_production.py) |
| **7. Operations & response** | Weekly CI run catches newly published dependency advisories; findings get a write-up, a regression test and a prevention step | [Finding 001](findings/001-search-sql-injection.md) |

## The loop in practice

Two moments where the process caught something real:

1. **Vulnerable dependencies (phase 3).** The first pip-audit run flagged 13 advisories in
   `python-multipart` and `starlette`. The upgrade then changed how Starlette sends the session
   cookie and broke a test — the test caught a behaviour change, and the cookie flags were
   verified before the test was adjusted.
2. **SQL injection (phase 4, seeded on purpose).** It passed CI because the only search test was
   a happy-path test and Bandit rated the pattern medium. The fix added hostile-input tests and a
   CI rule that blocks string-built SQL at any severity — so the same class of bug now fails the
   build.

## Deployment decisions

| Decision | Why |
|---|---|
| **Not hosted publicly** | Open sign-up would mean moderating strangers' content and holding their personal data (GDPR), on a free tier with known open risks (no global rate limit, no MFA). Not worth it for a portfolio demo; screenshots in the README instead |
| Target if hosted: Render free web service + Neon free Postgres | Free tiers, GitHub integration, managed TLS; Neon's free database does not expire |
| No `--proxy-headers` | `X-Forwarded-For` is client-controlled; trusting it would let an attacker rotate fake IPs past the login throttle. Trade-off recorded as S1 in the threat model |
| Stylesheet linked by relative path | `url_for()` would build `http://` URLs behind the TLS proxy, blocked as mixed content |
| Tables created at start-up | Fine for one small schema; a real project would use migrations (Alembic) |

## Known limits

Kept honest in the [threat model § 6](threat-model.md#6-open-risks-and-next-steps): no global
rate limit, no audit log, no MFA, in-memory throttle. These are the reasons the app is
deploy-ready rather than publicly hosted.
